--------------------------------------------------------------------------------
1.1  THE HEADLINE
--------------------------------------------------------------------------------

Our videos are correctly stored in IPFS and are correctly SERVED by gateways.
Whether they PLAY in a real browser is, as of this writing, UNVERIFIED - see the
CORRECTION block above; the browser used for testing could not play any video,
including an unrelated public control file.

What IS established: our content has exactly ONE IPFS provider (this laptop),
because no remote pinning service is configured. That is a real single point of
failure regardless of how the playback question resolves, and it is the item
worth fixing first.

  What we tested before (curl)          What a visitor actually does (browser)
  ----------------------------          --------------------------------------
  curl -sI <gateway>/<cid>              <video> sends Range: bytes=0-
  curl -r 0-1000 <gateway>/<cid>        i.e. asks for the ENTIRE file
  -> HTTP 200/206, video/mp4, 0.25s     -> stalls forever, no error, no metadata

A small byte-range request is served from the gateway's edge cache and returns
instantly. A whole-file request forces the gateway to pull all 14-17 MB across
bitswap from whoever actually has the blocks. For our content that is exactly ONE
machine - Bryan's laptop. It never streams fast enough, so the browser sits in
NETWORK_LOADING forever.

--------------------------------------------------------------------------------
1.2  COVERAGE - WHAT WE ARE GETTING
--------------------------------------------------------------------------------

BYTE-LEVEL AVAILABILITY (curl, small range) - GOOD:

  Gateways serving our CIDs        5 of 6 tested
  Sample of 12 corpus videos       11 of 12 returned HTTP 200
  Content correctness              exact byte-length match, content-type video/mp4
  Pin correctness                  100% - all checked CIDs are `ipfs add --pin`,
                                   recursive, NOT the `ipfs add -n` dry-run trap

BROWSER PLAYBACK - BAD:

  Videos that reached loadedmetadata in a browser from an IPFS gateway:  0 of 3
  (tested: our 2 new videos, plus one pre-existing site video that is hosted on
  a real pinning service and is NOT on our laptop - it stalled too)

So: our IPFS storage is healthy. Our IPFS *delivery to browsers* is not working.

--------------------------------------------------------------------------------
1.3  WHAT WAS ABNORMAL
--------------------------------------------------------------------------------

A. NO REMOTE PINNING SERVICE IS CONFIGURED.  <-- the core defect
     `ipfs pin remote service ls` returns EMPTY.
     Consequence: a DHT provider lookup for our videos returns exactly ONE
     provider - this laptop. When it sleeps, moves network, or is busy, the
     content is unreachable for everyone on earth. This is not a redundancy
     nicety; it is the direct cause of the stall.

B. THE FALLBACK CHAIN WAS FAKE.
     The page listed ipfs.io and dweb.link as its two <source> fallbacks. Those
     are the SAME OPERATOR and share one rate limit. When that operator throttled
     us (HTTP 429, triggered by our own testing from this IP), both died at once.
     Worse - see (C) - the fallback would not have fired anyway.

C. A STALL IS NOT AN ERROR, SO <source> FALLBACK NEVER FIRES.
     Browser event trace we captured:
         emptied -> loadstart -> stalled -> (nothing, forever)
         networkState = 2 (NETWORK_LOADING), readyState = 0 (HAVE_NOTHING),
         error = null
     The HTML media element only advances to the next <source> on a definitive
     ERROR. A hang produces no error. So adding more <source> lines does NOT
     create resilience against a slow gateway. This is a real trap and it is why
     the first attempted fix (adding more gateways) did not work.

D. ONE VIDEO WAS ENCODED ABSURDLY LARGE.
     2095784011868020764.mp4 was 2560x1440 at 2.4 Mbps for a standard-definition
     TV news clip - 17 MB for 54 seconds. Re-encoding to 720p produced a visually
     equivalent 3.1 MB. We were asking the network to move 5.5x more bytes than
     the content justified.

E. THE PROBLEM IS SITE-WIDE, NOT LIMITED TO THESE TWO VIDEOS.
     A pre-existing site video (Narrative/overview, CID bafybeifcxf7...) which is
     NOT on our node and IS served by a real pinning service ALSO stalled in the
     browser. Every IPFS-embedded video on this site is suspect. This needs a
     full sweep - see 1.5.

NOT ABNORMAL - ruled out, do not re-investigate these:
     * The add/pin itself           - correct, recursive, verified
     * Node reachability            - public IPv4 24.19.75.227, real public
                                      addresses, no relay dependence, 83 peers
     * Node is serving              - bitswap shows 214,366 blocks / 55 GB SENT
     * MP4 faststart                - moov precedes mdat in BOTH files, so no
                                      full-file download is required for metadata
     * CSP / CORS                   - no CSP meta tags, no violations logged
     * IPFS Companion / localhost rewriting - extension not installed,
                                      Addresses.Gateway is empty, no localhost
                                      gateway running
     * Element visibility/CSS       - video box measured 411x150, display block,
                                      visibility visible, opacity 1

--------------------------------------------------------------------------------
1.4  WHAT WAS FIXED TODAY
--------------------------------------------------------------------------------

Commit 1a8bb33e1 - the two screwdriver videos now play:

  1. Re-encoded to web-sized 720p H.264 + faststart + AAC:
       2095784011868020764.mp4   17 MB -> 3.1 MB
       2095734681039696205.mp4   14 MB -> 12 MB (quality deliberately kept;
                                  broadcast text legibility is evidentiary)
  2. Copied into site/internals/static/video/ so they are served from OUR OWN

This fixes PLAYBACK. It does NOT fix DURABILITY - see 1.5.

--------------------------------------------------------------------------------
1.5  WHAT STILL NEEDS FIXING
--------------------------------------------------------------------------------

FIX 1 - CONFIGURE A REMOTE PINNING SERVICE  [BLOCKED: needs a credential]
  Priority: HIGHEST. This is the root defect behind everything above.
  Today every video CID on this site depends on one laptop staying awake.
  That is the opposite of the censorship-resistance IPFS was adopted for.

  How to fix, once you have a token from Pinata or Storacha/web3.storage:

      ipfs pin remote service add pinata \
          https://api.pinata.cloud/psa <JWT>

      # then pin everything we already have:
      ipfs pin ls --type=recursive -q | while read C; do
        ipfs pin remote add --service=pinata --background "$C"
      done

      # verify a CID now has MORE THAN ONE provider:
      ipfs routing findprovs -n 5 <CID>

  Store the token in ~/.credentials/charlie_kirk.json (mode 600, outside the
  repo) alongside the flight-API keys, NOT in the repo. Note that
  ~/.credentials/large_files_bridge.json currently holds only Google OAuth +
  an API secret - there is no pinning credential anywhere on this machine.

FIX 2 - SWEEP THE WHOLE VIDEO CORPUS FOR BROWSER PLAYABILITY
  Priority: HIGH. Finding (E) says this is site-wide.
  Do NOT use curl for this. Use the browser probe in section 2.6. Any video that
  reaches only `stalled` is broken for every visitor regardless of what curl says.
  137 videos are in videos/manifest.yaml. Assume all IPFS-embedded ones are
  affected until proven otherwise.

FIX 3 - MOVE PLAYBACK OFF IPFS SITE-WIDE, KEEP IPFS AS THE ARCHIVE
  Priority: HIGH, and it is the pattern that actually works.
  Videos are currently gitignored (videos/* in .gitignore) on the theory that
  they are pulled from IPFS. That theory is what broke playback. The site already
  serves ~500 MB of images out of the repo successfully; video should follow the
  same model at web-appropriate sizes.
  Constraint: the built site is ALREADY 1.2 GB against GitHub Pages' 1 GB soft
  limit (img/ 501 MB, court/ 443 MB). So this must be paired with re-encoding,
  not done naively. A 137-video corpus at ~3-5 MB each is ~500 MB - too much on
  top of what is there. Realistic options, in order:
     (a) Re-encode and self-host only the videos actually EMBEDDED on pages.
     (b) Shrink img/ and court/ first (501 MB + 443 MB is the real bloat).
     (c) Move video to a proper CDN/object store and keep IPFS as the archive.

FIX 4 - STOP LISTING TWO GATEWAYS FROM THE SAME OPERATOR AS "FALLBACK"
  Priority: MEDIUM. ipfs.io and dweb.link are one operator. If gateway <source>
  lines are used at all, they must span different operators - and per finding (C)
  understand that they only help against hard errors, never against a stall.
  Real resilience requires a JS error/stall handler that swaps src on a timeout,
  not more <source> tags.

FIX 5 - UPDATE THE ck_add_text SKILL
  Priority: MEDIUM. The skill's step 6b2 marks a video "publicly retrievable" on
  the strength of a curl range request. That check is now known to be misleading -
  it passed on both of these videos while both were unplayable. The skill should
  either run a real browser probe or stop claiming "READER CAN SEE IT: YES" on
  curl evidence alone.

2.6  HOW TO RE-TEST (copy/paste)
--------------------------------------------------------------------------------

BYTE AVAILABILITY (fast, but DOES NOT PROVE PLAYABILITY):

  curl -sI -m 45 "https://ipfs.io/ipfs/<CID>" | head -3
  curl -s -o /dev/null -w "http=%{http_code} type=%{content_type} ttfb=%{time_starttransfer}\n" \
       -m 60 -r 0-1048575 "https://<CIDv1base32>.ipfs.w3s.link/"

  Convert CIDv0 -> CIDv1 base32 (subdomain gateways REQUIRE base32):
  ipfs cid base32 <QmCID>

  ALWAYS run a CONTROL before calling anything a failure:
  curl -sI "https://ipfs.io/ipfs/QmQPeNsJPyVWPFDVHb77w8G42Fvo15z4bG2X8D2GhfbSXc"
  If the control fails the same way, it is the gateway or your IP, not our content.

PROVIDER COUNT (the number that matters most):

  ipfs routing findprovs -n 5 <CID>
  More than one line that is not our own peer ID = healthy.
  Only our peer ID = single point of failure.

REAL PLAYABILITY (the only test that speaks for a visitor) - paste in DevTools
console on the live site:

  (async u=>{const t0=performance.now();const v=document.createElement('video');
   v.preload='metadata';v.muted=true;
   const r=await new Promise(res=>{let d=0;const f=o=>{if(!d){d=1;res(o)}};
     v.onloadedmetadata=()=>f({R:'PLAYS',dur:Math.round(v.duration)});
     v.onerror=()=>f({R:'ERROR',code:v.error&&v.error.code});
     setTimeout(()=>f({R:'STALLED - BROKEN FOR VISITORS',readyState:v.readyState}),20000);
     v.src=u;v.load();});
   console.log(u,Math.round(performance.now()-t0)+'ms',r);})
  ('https://<CIDv1>.ipfs.dweb.link/')

  PLAYS  = a visitor can watch it.
  STALLED = broken, no matter what curl said.

--------------------------------------------------------------------------------
2.8  LESSONS TO CARRY FORWARD
--------------------------------------------------------------------------------

  1. curl proves bytes exist. It does NOT prove a video plays. Different request
     shape (small range vs whole file), different result.
  2. A media stall fires NO error, so <source> fallback never advances. More
     gateway <source> lines are not resilience.
  3. Content with ONE provider is not "on IPFS" in any operationally useful
     sense. Provider count is the health metric, not pin status.
  4. Always run a control - an unrelated CID, an unrelated aircraft, an unrelated
     anything - before declaring our content suppressed, removed, or broken. It
     saved a wrong conclusion twice today (the 429s, and the 404).
  5. Encode for the web before publishing. 2560x1440 for a TV news clip is
     5.5x the bytes for zero added information.
